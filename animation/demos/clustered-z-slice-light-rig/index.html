为什么在实现现代三维引擎的分簇前向渲染（Clustered Forward+ / Froxel Light Culling，如 DOOM idTech、Three.js WebGPU、Godot 4）时，如果把相机近裁剪面 `z_near = 0.10 m` 到远裁剪面 `z_far = 1000.0 m` 按视空间深度直接做 **17 等份线性切分（Linear Depth Slicing，每片厚度固定为 `Δz = 999.9 / 17 = 58.82 m`）**，整个室内房间、角色周围与街道近中景（`0.10 m ~ 58.92 m`）的所有点光源就会全部挤爆第 0 号切片（Slice 0 吞下 `12/17` 个对数深度层，产生 **`12.00×` 的光源列表溢出碰撞**），而远景居然有 **11 个深度切片空空如也（`0` 光源）**？因为透视视锥体的横向截面随深度 `z` 成正比放大：要让每个三维簇体素（Froxel）都保持接近正方体的自相似宽高比（`Δz / z = const`），切片厚度必须随深度指数递增！而 Olsson 等人（HPG 2012）提出的对数深度切片（Logarithmic Z-Slicing）按几何级数划分边界 `z_k = z_near · (z_far / z_near)^(k / N_z)`，并在片元着色器中仅用一次预计算乘加 `s(z) = ⌊ln(z)·scale + bias⌋` 即可完成 `O(1)` 寻址，使全部 17 个深度切片保持恒定的自相似比 `r = 1.7191` 并严格各分担 `1/1` 个光源带（`0/17` 切片过载或闲置）！An original 17-slice 3D froxel light-culling bench compares Olsson logarithmic Z-slicing against linear view-space depth slicing.

This bench evaluates deterministic Olsson, Billeter & Assarsson (HPG 2012) logarithmic/self-similar frustum Z-slicing (`s(z) = floor(ln(z)*scale + bias)`) versus naive linear view-space depth slicing and explicit plane-array search across 17 frustum depth slices (z ∈ [0.10, 1000.0] m).
