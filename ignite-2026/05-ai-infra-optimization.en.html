Data flow · 双场景推理执行链路 (1–7) Data flow · Dual-Scenario Execution Path (1–7)

  1. 前缀哈希亲和接入：AI Gateway 按会话与共享前缀哈希路由至目标实例以最大化 KV 缓存命中，Cobalt 200 卸载主机侧协议解析与分词计算。 Prefix-affinity ingress: AI Gateway routes sessions by prefix hash to maximize KV cache locality while Cobalt 200 offloads host serialization and tokenization.
  2. 前置校准概率过滤：Decision-1.1（$0 输出计费）在网关侧完成高频分类与合规门控，仅将复杂生成请求放行至后端 GPU 池。 Pre-inference cascade filter: Decision-1.1 ($0 output cost) resolves routine triage and policy checks before consuming backend GPU compute.
  3. 多级存储前缀 KV 复用：HBM / DRAM / NVMe 分层缓存直接复用 System Prompt 与 MCP Schema 的 KV 张量，省去 70%–90% 重复 Prefill 计算。 Tiered Prefix KV reuse: HBM/DRAM/NVMe cache layers reuse static System + MCP Schema KV tensors, cutting 70%–90% redundant Prefill compute.
  4. Prefill / Decode 算存分离：专用 Prefill 节点计算增量输入并经 RDMA 传输 KV 块至高访存带宽 Maia 300 解码池，隔离长输入对流式 TPOT 的抖动干扰。 Disaggregated Prefill/Decode: Compute-dense Prefill nodes stream incremental KV blocks over RDMA to high-bandwidth Maia 300 Decode pools for jitter-free TPOT.
  5. Serverless 托管伙伴池弹性调用：波动型或中低并发的 DeepSeek、Kimi 与生视频请求直接调用 Foundry 托管 Fireworks / Baseten / fal 接口。 Serverless partner burst endpoints: Variable or moderate-volume DeepSeek, Kimi, and video DiT traffic calls managed Fireworks / Baseten / fal endpoints in Foundry.
  6. 多节点无损 RDMA 自托管集群：高吞吐稳态负载部署于 AKS GPU，采用机内 NVLink（TP）+ 跨机无损 IB/RoCEv2（EP / 序列并行）分层通信。 Multi-node lossless RDMA cluster: High-utilization workloads run on AKS GPU pools using intra-node NVLink (TP) and inter-node lossless IB/RoCEv2 (EP/SP).
  7. 上游慢依赖治理与自动化排障：Azure Catalyst 重构慢速业务 API，SRE Agent 持续监控 GPU 硬件健康度、PFC 死锁指标与端到端 P99 SLA。 Upstream refactoring & automated SRE: Azure Catalyst modernizes slow upstream APIs while SRE Agent monitors GPU health, RDMA telemetry, and P99 SLAs.

Design points · 架构师关键设计决策 Design points / Solution Architect Decisions

  • 物理拆池消除 TTFT 与 TPOT 跨阶段资源争用：将算力密集型（Compute-Bound）Prefill 与显存带宽密集型（Memory-Bandwidth-Bound）Decode 拆分为独立弹性池，避免长文档 RAG 抢占解码流。 Isolate Compute-Bound Prefill from Memory-Bound Decode: Disaggregating Prefill and Decode pools prevents long-context RAG requests from stalling active token generation streams.
  • 区分稀疏 MoE 与生视频 DiT 的显存瓶颈：MoE 单 Token 虽仅激活 37B 参数，但全量 671B–1T 专家权重须常驻聚合 HBM；14B–30B 视频 DiT 则受十万级 3D 时空 Token 激活值主导，须配置 Ulysses/Ring 序列并行。 Size HBM differently for sparse MoE vs video DiT: MoE requires aggregate HBM for all 671B–1T total weights despite 37B active parameters, whereas 14B–30B video DiTs are dominated by 100K+ 3D token activations requiring Ulysses/Ring SP.
  • 严格对齐并行策略与物理网络层级：高频逐层同步的 TP 限制在单节点 NVLink 域内；跨节点 MoE All-to-All 与序列并行须运行在 IB (SHARP) 或启用 PFC + ECN/DCQCN 的轨道优化无损 RoCEv2 上。 Align parallelism dimensions to physical fabric tiers: Confine per-layer synchronous TP inside intra-node NVLink; run cross-node MoE All-to-All and video SP over IB (SHARP) or rail-optimized lossless RoCEv2 (PFC + ECN/DCQCN).
  • 按持续 GPU 利用率判定托管与自建临界点：周均 GPU 利用率低于 45%–55% 时优先使用 Foundry 托管端点按量计费；高于该阈值或有 VNet 机密计算要求时再采用 AKS GPU + Mixed MIG。 Select Serverless vs AKS GPU by utilization breakeven: Favor Foundry serverless partner APIs below 45%–55% sustained weekly GPU utilization; transition to AKS GPU + Mixed MIG for steady high load or confidential VNet residency.

SCENARIO 01 · TOKEN INVOCATION LATENCY

Token 调用延迟优化 Token Invocation Latency Optimization

深入拆解大模型两阶段推理物理瓶颈：受算力限制（Compute-Bound）的 Prefill 首字延迟（TTFT） 与受显存带宽限制（HBM Bandwidth-Bound）的 Decode 逐字延迟（TPOT / ITL），通过四层全栈协同消除长上下文智能体卡顿。 Deconstructing two-phase LLM inference physics: Compute-bound Prefill (TTFT) versus HBM memory-bandwidth-bound Decode (TPOT / ITL), and eliminating multi-turn agent stalls via a 4-layer optimization stack.

TTFT & TPOT Stack

第一层：Prefill-Decode (PD) 算存分离架构 Layer 1: Prefill-Decode (PD) Disaggregation

Zero P/D Interference
⚙️ 架构机制Architecture Mechanics
  • 将计算密集型 Prefill 实例池 与显存带宽敏感型 Decode 实例池 物理拆解，独立设置并行策略（例如 Prefill 高并发算力切分、Decode 大 Batch + 高 HBM 带宽）。Physically decouples compute-intensive Prefill pools from memory-bandwidth-sensitive Decode pools with independent parallelism & batching policies.
  • Prefill 完成后通过高速 RDMA 单边传输将分页 KV 块流式推送至 Decode 节点，彻底根除长上下文请求插入导致的解码流停顿（Prefill-Decode Interference）。Streams prefilled paged KV blocks over high-speed RDMA to Decode nodes so incoming 64K RAG turns never pause ongoing streaming tokens.
🏢 业务场景Business Scenarios
  • 长上下文合同审查与研发 Coding Agent：输入高达 48K–128K Token，输出仅数百 Token（高 P/D 比，例如 4P:1D 弹性扩缩）。Long-Context Legal & Coding Agents: 48K–128K input prompts paired with concise tool calls (high Prefill-to-Decode ratio, e.g., 4P:1D pool scaling).
  • 实时语音客服（GPT Live 1 / Realtime Flash 1）：严苛要求 TPOT P99 < 25ms，绝不允许后台知识库检索大 Prompt 拖慢实时语音流。Real-Time Voice Agents: Strict P99 TPOT < 25ms SLA where heavy background RAG prompts cannot jitter live audio synthesis.
竞争优势Competitive Advantage
  • 相比传统单体混部推理引擎，在相同 TTFT 与 TPOT 双重 SLA 约束下，GPU 集群有效好吞吐（Goodput）可提升 1.8× – 2.6×。Delivers 1.8× – 2.6× higher GPU Goodput under strict dual TTFT + TPOT SLAs compared to monolithic colocated serving.
🧭 SA 落地要点SA Implementation Guardrails
  • 在 Foundry 托管侧优先为高并发稳态生产流配置 Provisioned Throughput (PTU) 锁定确定性延迟；自建 AKS 侧结合 vLLM / SGLang + Mooncake/NIXL 启用跨节点 RDMA KV 传输。Use Foundry Provisioned Throughput (PTU) for deterministic enterprise SLAs; on self-hosted AKS, pair vLLM / SGLang with RDMA KV transport over RoCEv2/IB.

第二层：不可变前缀缓存（Prefix Caching）与多级 KV Cache 亲和 Layer 2: Prefix Caching & Tiered Session KV Cache Locality

70%–90% Prefill Cut
⚙️ 架构机制Architecture Mechanics
  • 基于 RadixAttention / Hash Block 匹配前缀 Token 块；结合会话亲和一致性哈希路由与 三级 KV 存储池（GPU HBM → Host DRAM → 本地 NVMe），跨轮次直接复用已计算的 KV 张量。Matches prefix token blocks via RadixAttention/block hashing alongside session-affinity routing and 3-tier KV pools (GPU HBM → Host DRAM → NVMe).
  • 必须遵循严格的 不可变前缀优先排布铁律：系统指令 → 字典序固定的 MCP 工具 Schema → 静态业务本体规则 → 动态用户消息与本轮检索片段。Requires strict immutable-first prompt ordering: System Prompt → Sorted Frozen MCP Tool Schemas → Static Domain Ontology → Dynamic Turn Context.
🏢 业务场景Business Scenarios
  • 多步 ReAct / 工具编排智能体：单次任务连续执行 6–12 轮工具调用，前 90% 的上下文完全不变或仅在尾部追加，KV 命中率稳定超 80%。Multi-Step ReAct & Tool Agents: 6–12 consecutive tool turns where 80%+ of prior context and tool schemas remain identical.
竞争优势Competitive Advantage
  • 首字延迟 TTFT 直降 65%–85%，同时大幅削减缓存命中的输入 Token 计费成本（Cached Input Token Discount）。Slashes TTFT by 65%–85% while unlocking deep Cached Input Token billing discounts on Foundry APIs.
🧭 SA 落地要点SA Implementation Guardrails
  • 最高频反模式警告：严禁在 System Prompt 第 1 行拼入精确到秒的 current_time、随机 trace_id 或每轮乱序序列化 JSON 工具列表——这会导致后续几万 Token 的前缀缓存 100% 失效！动态元信息一律后置到尾部消息。Top Anti-Pattern Alert: Never inject per-second timestamps, random UUIDs, or unsorted JSON tool keys at the top of the System Prompt—doing so invalidates 100% of downstream KV cache! Append dynamic metadata at the tail.

第三层：级联路由（Decision-1.1 / Model Router）与投机解码 Layer 3: Cascaded Routing, PagedAttention & Speculative Decoding

Zero-Waste Compute
⚙️ 架构机制Architecture Mechanics
  • 入口使用 Microsoft-Decision-1.1（GA，输入仅 $0.042/1M，输出 Token $0） 与 Model Router 完成意图分类、安全门控与复杂度分流，避免用重型推理模型处理简单路由轮次。Offloads classification, guardrails, and discrete routing to Microsoft-Decision-1.1 (GA, $0.042/1M input, $0 output tokens) + Model Router.
  • 解码阶段采用 PagedAttention 连续批处理消除显存碎片，并结合 投机解码（Speculative Decoding / MTP 多 Token 预测）：一次 HBM 权重读取并行验证 3–5 个候选 Token，突破访存带宽上限。Pairs PagedAttention continuous batching with Draft-Target / MTP Speculative Decoding to verify 3–5 tokens per single HBM weight read pass.
🏢 业务场景Business Scenarios
