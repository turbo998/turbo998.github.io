Six layers, one end-to-end critical path

A faster GPU cannot repair a stalled network, invalid KV layout or low useful-work availability. Follow the critical path through six layers, then use the original calculators to change one assumption at a time.

  1. Classify the limit: compute, HBM capacity, bandwidth or queueing.
  2. Track bytes and ownership across NVLink, fabric and KV handoff.
  3. Overlap only independent work; check transient memory and correctness.
  4. Evaluate cost per useful token at a fixed quality and tail-latency SLO.
Evidence boundary: the source reports analytical CPU/offline simulation (synthetic), not fresh accelerator measurements. Its own-offline and independently_reproduced=true labels describe that original CPU verification only. This localization does not rerun upstream experiments.

L1 · Silicon & HBM roofline

P ≤ min(Ppeak, BHBM × I); I = FLOPs / bytes

A kernel is bandwidth-bound below the ridge point I = Ppeak/BHBM, and compute-bound above it. Reusing tiles in SRAM raises arithmetic intensity; increasing batch size can do the same, but consumes KV capacity and increases queueing latency. Peak tensor throughput is not application throughput.

Measure bytes moved, register pressure and occupancy together; a larger tile can spill registers and erase reuse gains.

Primary documentation: CUDA Programming Guide

L2 · Scale-up & scale-out fabric

Tring ≈ 2(p−1)α + 2(p−1)S/(pB)

NVLink is the scale-up interconnect; NVLS uses NVLink Switch reduction support. SHARP moves supported reductions into the scale-out fabric. UEC addresses Ethernet transport and congestion, not arithmetic offload. Ring AllReduce amortizes bandwidth well for large tensors but its latency term grows with rank count.

S is tensor bytes, p ranks, α per-hop startup and B effective link bandwidth. Tree/offload gains depend on supported datatypes, topology and contention; do not extrapolate a lookup table to arbitrary fabrics.

Primary documentation: NCCL NVLS · SHARP · Ultra Ethernet Consortium

L3 · Distributed training & optimization

Tstep ≈ Tcompute + max(0, Tcomm − Toverlap)

FSDP2 shards parameters, gradients and optimizer state, then all-gathers parameters when needed. Prefetch trades extra live memory for overlap. DualPipe schedules bidirectional pipeline work to hide communication and bubbles. Muon orthogonalizes matrix updates; its optimizer cost and convergence behavior must be assessed separately from pipeline speed.

The source example exposes 4.0 ms of a 25.0 ms outer-DP reduction: 1−4/25 = 84.0% hidden. This is an offline fixture, not a GPU measurement; 84% communication overlap is not 84% whole-step speedup.

Primary documentation: FSDP2 · DualPipe · Muon

L4 · KV placement & attention execution

MKV = 2 × L × T × Hkv × D × b; Txfer ≥ bytes/B

Mooncake separates KV storage and transfer from compute; NIXL abstracts data movement backends. FlashMLA specializes attention execution around compressed latent KV representations. FP4 KV reduces bytes but requires scale metadata, compatible kernels and quality checks. The standard multi-head KV formula shown here is not the MLA latent-cache formula.

L = layers, T = cached tokens, Hkv = KV heads, D = head width, b = bytes per element. With equal per-layer sizes, 56 FP8 + 8 BF16 layers use 72 rather than 128 byte-units: 43.75% less. Skipping 11 of 16 prefilled pages removes 68.75% of those writes, not all serving traffic.

Primary documentation: Mooncake · NIXL · FlashMLA

L5 · Speculation & constrained decoding

Speedup ≈ E[accepted tokens + 1] × Ttarget / (Tdraft + Tverify)

EAGLE-3 proposes draft tokens for target-model verification. High acceptance alone is insufficient: draft and verification costs must be lower than the target steps avoided. XGrammar masks tokens that violate a grammar. Syntactic validity does not prove factual correctness or authorization, and grammar work belongs in the latency budget.

Compare end-to-end goodput at the same quality and tail-latency SLO. Larger trees can increase useful accepted tokens while wasting verification compute and KV memory.

Primary documentation: EAGLE-3 · XGrammar

L6 · Reliability, availability & cost

$/1M = ($/GPU-hour) × 10⁶ / (tok/s × ETTR × 0.85 × 3600)

NVRx recovery and RAS telemetry reduce lost work only when detection, checkpoint and restart paths are tested. FinOps should divide total cost by useful delivered work, not peak capacity. The calculator uses three years, electricity at $0.065/kWh and a fixed 0.85 serving-utilization factor; these are scenario assumptions, not vendor quotes.

TCO = GPU count × CapEx/GPU + GPU count × IT kW/GPU × PUE × 26280 hours × electricity rate. ETTR discounts useful compute and tokens, not powered-on hours. Network, staffing and financing costs are not separately modeled.

Primary documentation: NVRx
