关键架构师洞察：为什么在骁龙 X Elite 上运行 phi-4-mini 不会用到 NPU，而 phi-4-mini-reasoning 会？

实时目录核验表明：标准指令模型 phi-4-mini 目前没有发布 QNN NPU 变体，在 Copilot+ PC 上会自动路由至 Adreno X1-85 GPU 的 WebGpuExecutionProvider（磁盘 3.72 GB / 显存占用 3.74 GB）；而推理增强版 phi-4-mini-reasoning 提供了 QuaRot + GPTQ 预量化包（2.78 GB），可直接跑在 Hexagon NPU（Priority 0） 上，体积反而小 25.3% 且不挤占图形渲染管线！

四大生产级工程避坑指南（SA 实测排障手册）

坑位 1：.NET 10 目标框架（TFM）不匹配导致 WinML EP 无法注册

使用 dotnet new console 默认生成的裸 <TargetFramework>net10.0</TargetFramework> 缺少 Windows WinRT / WinML 投影绑定，会导致动态 EP 发现失败或回退纯 CPU。修复方案：在 .csproj 中显式声明带 Windows SDK 版本的 TFM（例如 net10.0-windows10.0.26100.0 或 net8.0-windows10.0.22621.0），并明确指定 <RuntimeIdentifier>win-arm64</RuntimeIdentifier>（或 win-x64）。

坑位 2：phi-4-mini 与 phi-4-mini-reasoning 的静默 EP 路由分叉

许多开发者以为名称带 phi-4-mini 就一定跑在 NPU 上。实际上目录中 phi-4-mini（标准 Instruct）仅有 WebGPU（3.72 GB 磁盘 / 3.74 GB 显存）与 CPU 变体；而 phi-4-mini-reasoning（2.78 GB，QuaRot + GPTQ）才拥有原生 QNN NPU 变体。修复方案：需要低功耗后台常驻时请显式指定 phi-4-mini-reasoning、phi-3.5-mini (2.02G) 或 qwen2.5-coder-1.5b (1.06G)。

坑位 3：32 GB 统一内存仍触发 QNN 错误 5005（Windows Commit 水位耗尽）

在共享 LPDDR5x 的 Copilot+ PC 上，即便任务管理器显示还有“可用物理内存”，若浏览器标签页、容器或 IDE 已拉高系统 已提交内存（Commit Charge）逼近提交上限（Commit Limit），Hexagon QNN 驱动为 7B/14B 模型分配连续锁页缓冲区时会抛出 QNN context binary / allocation error 5005。修复方案：加载 deepseek-r1-14b (7.12G) 前确保剩余未提交内存余量 ≥ 10 GB，或启用系统自动管理分页文件并及时卸载空闲模型会话。

坑位 4：foundry-local-sdk-winml 与 foundry-local-sdk 命名空间覆盖冲突

Python 生态同时存在带动态 EP 下载能力的 foundry-local-sdk-winml 与不含 WinML 的基础包 foundry-local-sdk，两者共用同一顶级导入路径。若在同一虚拟环境先后安装，会导致文件互相覆盖、NPU EP 神秘消失。修复方案：使用全新虚拟环境仅安装其中一个；若已混装，务必先执行 pip uninstall -y foundry-local-sdk foundry-local-sdk-winml 再重装 foundry-local-sdk-winml。
